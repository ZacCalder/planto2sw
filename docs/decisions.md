# 設計決定

| # | 決定 | 原因 |
|---|---|---|
| 1 | 唯一寫入路徑是碌邊張的備份匯入（JSON / SW1. 轉移碼），不寫 Supabase | 匯入係 app 自己提供嘅功能；直接寫雲端會繞過佢嘅同步邏輯 |
| 2 | 純本機：瀏覽器單檔 + Python CLI，不做伺服器 | 與碌邊張「預設唔上傳」一致；個人開源不背凭證/隱私責任 |
| 3 | 官方 Open API / Finverse 等 aggregator 不走 | HKMA Open API Phase III/IV 與 IADS 只覆蓋存款戶口，不含信用卡；且需公司主體逐家簽約 |
| 4 | 不做網銀 screen scraping / app 逆向 | 凭證風險 + 2FA 每兩天斷一次（Planto 自己都如此） |
| 5 | Planto CSV 作歷史基線；即時性靠日後的通知監聽補 | CSV 手動觸發、無增量 |
| 6 | log id 確定性（sha1 → 9e14 區間數字），已存在的 id 以 app 內版本為準 | 可重複跑、用戶手改優先 |
| 7 | rate/rebate 由工具算好寫入；來源優先：通道規則（config `channel_rules`，如 Pulse 內地經微信/支付寶只有基本率）→ 用戶覆蓋（config `rate_overrides` / 瀏覽器版費率表手改）→ **費率引擎**（復刻碌邊張 `FC`，輸入第 2 步設定）。用戶手動記賬學到的率不再作來源，只在與引擎不符時提示「檢查第 2 步設定」。兩個實現順序相同，`tests/compare.py` 守住；引擎本身由 `tests/engine_check.py` 對本機快取嘅碌邊張 app 2.0.4 bundle 回歸（引擎已凍結喺呢版，見決定 22） | app 儲賬後不重算；記賬存的就是 `FC(...).rate`，所以復刻它即等於 app 自己記（限 2.0.4；app 之後改計法會有出入，見決定 22）；明確覆蓋高於推斷值（2026-09-11 定） |
| 13 | Guru 剩餘額度、EveryMile 季度累計按**日期順序回放**：快照裡全部記賬先計入（同 id 將被重新生成的那些除外，免計兩次），新記賬按日期逐筆加入，每筆用加入時的剩餘額度算混合率 | app 在記賬當下用「當時已有的全部記賬」算；歷史匯入只能模擬「按時間逐筆輸入」。與 app 的差別：EveryMile 季度取記賬所在季度而非「今天」所在季度。全卡模型（`guru_monthly_top_card=false`）與 app 卡片頁的 Guru 年度 RC 用同一公式（`hz` memo），兩者一致 |
| 15 | Travel Guru 回放可切換（config `guru_monthly_top_card` / 第 2 步開關，**預設 false**）：false = 所有合資格 HSBC 卡的外幣簽賬合併計算、共用年度上限（條款 9c，與 app 一致）；true = 每個自然月只有外幣簽賬最高的那張 HSBC 卡拿 Guru——**這是已否決的舊讀法，開關只保留用來重現舊數字**。基準 RC + 基準日照 app 語義（基準日前的記賬不計；開 true 時當月最高卡按整月判）；回放嚴格按日期順序 | **歷史記錄**：2026-09-11 定這條時預設 true，理由是「兩種讀法都說得通，未確認」；2026-09-12 已否決——條款 9c 明文合併計算，「最高一張卡」是對 9d 的誤讀，預設改為 `false`，見決定 19 |
| 14 | 快照裡已有同 id 但**場景不同**的記賬：整筆不重新生成（狀態 `kept` / `kept-existing`），回放也用 app 裡那個場景 | 用戶可能在 app 裡改過分類（例如工具判 local、用戶在 app 裡改成 dining）；決定 6 的「用戶手改優先」要延伸到費率回放，否則 Guru 額度會被錯算 |
| 8 | 退款：配對後兩筆一起刪；未配對寫成**負數記賬**（amount、rebate 皆負，場景照原消費分類） | 網頁版實測：匯入負數 amount 後追蹤頁正常淨計（$1,000 消費 + $-100 退款 = 簽 $900、回贈 +$40）。注意 app 自己的記賬表單打唔到負數，只能靠匯入 |
| 16 | 第 2 步暴露 `promoRegs`（regId 來自 `merchantOffers[].offers[].reg`，未剔 = 寫 false 退出）與 `milestoneEnroll`（id 來自 `cardData.milestonePromos`，勾選 = `{enrollDate: 日期或 null}`）；`cardSettings`（結單日、到期日等）不做編輯界面，原樣帶回 | 排行榜頁與卡片頁的登記按鈕就是改這兩個鍵；日期類設定在 app 裡填更順手 |
| 17 | 瀏覽器版把卡對應（按 Planto 帳戶名）、費率覆蓋和自訂商戶規則記在 `localStorage`（`p2s_cardMap` / `p2s_rates` / `p2s_rules`，私人規則不入 repo、不寫入轉移碼）；未預置的帳戶按 Planto `Bank Name` → 發卡行 + 卡名關鍵字猜一次，唯一命中才預選 | 91 張卡不可能全預置；存款戶口永遠不會命中卡名 |
| 9 | CNY 內地消費以地區優先（travelCN），支付方式只作次級信號；但 Pulse 內地按通道給率：`SALES:`（網上卡號）、微信、支付寶無 +2%、無最紅自主，Travel Guru 照計（`channel_rules` 的 `no-bonus` 模式 = 引擎去掉 pulseReg 和 vs）；只有 `APPLEPAY` / `QR` 銀聯拿全額 | 銀行 T&C 按地區分場景，按通道分是否享額外獎賞。app 沒有「內地但無加成」的類別，場景仍記 travelCN，rate 由我們寫死；app 的 cap／Guru 用量會把這些筆也算入，方向是提早警告 |
| 10 | 優惠登記等設定由用戶在工具第 2 步填，寫入轉移碼；Planto 沒有此資料 | 匯入係整份覆蓋，快照缺設定會把用戶的設定沖掉 |
| 11 | 與用戶已手動記的賬去重（同卡、±1 天、原幣金額一致或港幣差 1% 內） | 實測出現同一筆消費手動記過又被匯入一次 |
| 12 | RewardCash 餘額不寫入碌邊張，留作對賬校驗 | app 沒有「已得獎賞」欄位 |
| 18 | **2026-09-12：暫停「匯入記賬」這條路，工具只做「查回贈」**：費率引擎查率（第 2／3 步）＋ `rewardcash_recon.py` 對賬。匯入功能保留可用，但唔再推進，亦唔再用嚟同步真實交易 | 碌邊張儲存記賬之後唔會重算（決定 7、22），而匯入係整份覆蓋、而且不可逆地把 rate/rebate 寫死；分類判錯、設定填錯、或者引擎凍結之後 app 改咗計法，每次匯入都會累積難以撤銷嘅錯值。另外 log id 不含場景，所以匯入之後想改分類，要先在 app 裡刪記賬先（見決定 14），修正成本高。查率同對賬唔寫入碌邊張，唔會改到 app 入面嘅資料 |
| 19 | **2026-09-12：決定 15 嘅「每月最高一張卡」讀法係錯嘅，`guru_monthly_top_card` 由 `true` 改為 `false`**（`config.example.json` 同 `index.html` 嘅 `GURU_MONTHLY_TOP_CARD`）。✅ 已改，兩處都係 `false` | 重新讀滙豐 Travel Guru 簽賬獎賞條款第 9 條：9c 講明名下多於一張合資格卡時，所有合資格簽賬合併計算，即係合併池；9d 講嘅係額外獎賞錢按月誌入上個曆月累積合資格簽賬淨額最高嗰個卡戶口，只決定入邊個戶口，唔決定邊啲簽賬賺得到。之前係將 9d 嘅「最高」誤當成賺取條件。決定 15 嘅「兩種讀法都說得通」已經唔成立 |
| 20 | **2026-09-12：`app-data.json` 改為用戶自備，永不內嵌、永不自動下載。**`index.html` 喺新增嘅「前置」步驟收檔，存喺 `localStorage` 嘅 `p2s_appdata`；`planto2sw.py` 用 `--app-data`（預設 `./app-data.json`）。兩邊都顯示該份嘅 `generatedAt` 同幾多日前，超過 `APP_DATA_STALE_DAYS`（30 日）警告。瀏覽器版有粒「一鍵攞最新」，撳咗先會去攞（頁面唯一一處 `fetch()`）；載入時、定時、重試、或者冇快取時一律唔會自己攞。`planto2sw.py` 完全唔連網；`tests/engine_check.py` 只用本機已有嘅 bundle 快取，唔會下載（`--download` 已刪，見決定 23） | 準確度：規則庫會更新，內嵌嘅快照一過期就顯示錯數；用戶自備加日期提示，過期就睇得到。順帶令內嵌嗰 63KB 快照消失，`index.html` 由 130KB 減到約 77KB |
| 21 | **2026-09-12：非官方聲明要喺每個用戶會落腳嘅表面出現，品牌名永不用嚟命名本工具。**README 三語各一句、`index.html` 頁首同頁尾、兩個 CLI 嘅 `--help`。倉庫名同工具名維持描述性（`planto2sw`），唔改名 | 工具名唔可以令人以為係碌邊張官方出品；描述性名唔會有呢個問題。原本全 repo 只有 README 第 8 行一句英文，而 `index.html` 係設計成可以單獨下載、脫離 README 傳播嘅，所以嗰度最要緊 |
| 22 | **2026-09-13：費率引擎凍結喺碌邊張 app 2.0.4（chunk `2565-b2d113f70d98cb47`，2026-09-11），唔再更新，亦唔拎走。**費率表上方、CLI 輸出、README 三語都明寫凍結日期同「以 app 為準」。基本費率同商戶優惠照讀用戶嘅 app-data.json；凍結嘅係硬編碼喺引擎入面嘅計法（逐張卡嘅分支、Travel Guru 年度 RC 上限、EveryMile 季度門檻）。**逐張卡嘅簽賬上限（`capAmt`／`sharedCap`／爆頂後嘅降率，例如 Pulse 內地嘅半年上限）完全冇建模**，簽過上限嗰部分嘅回贈會算多 | 碌邊張匯入時將每條記賬照寫入嘅樣儲存，之後永遠唔會重新判類別、亦唔會重算回贈：每條記賬顯示嘅回贈都係儲存咗嘅 `rebate`（讀法係 `rebate || 0`）；追蹤頁嘅總數會再用呢個儲存值反推有效率、按上限調低超出嘅部分，但冇任何地方會重算一條記賬嘅類別或者回贈，唯一會重算嘅情況係用戶逐筆打開一條記賬再按儲存，冇任何批量重算。所以工具一定要喺匯入之前自己分類、自己計好回贈，呢個就係工具有自己費率引擎嘅原因。拎走引擎（rate／rebate 留空交返 app 計）會令所有回贈顯示 HK$0，`rewardcash_recon.py` 亦靠 logs 嘅 rate／rebate。凍結加明示日期，令工具同 app 之間嘅出入睇得到 |
| 23 | **2026-09-13：公開方式、私人筆記、下載工具同上限說明。**(1) 公開版由一個乾淨嘅單一 commit 開新倉庫 `planto2sw`；原有開發倉庫保持私有。(2) 私人筆記只留本機，放喺 `private/`（`.gitignore` 已排除），唔入公開倉庫。(3) 刪走 `tests/engine_check.py` 嘅 bundle 下載功能（`--download`），只保留對本機已快取 bundle 嘅離線核對。(4)「一鍵攞最新」保留，但淨係用戶明確撳掣先會 fetch `app-data.json`（決定 20）。(5) 文件明寫逐張卡嘅簽賬上限冇建模（決定 22） | (1) 開發歷史入面有已經唔再適用嘅版本；用單一 commit 開新倉庫最乾淨。(2) 私人筆記唔屬於工具文件。(3) 引擎已凍結（決定 22），唔再需要對新版 bundle 重抓；公開倉庫唔提供抓取碌邊張前端嘅工具。(4) 撳一下就攞到當日最新規則庫，比手動另存嘅舊檔準；唔撳就唔會連網。(5) 免得有人以為上限已經計入：簽過上限嘅回贈會算多 |
